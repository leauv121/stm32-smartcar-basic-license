# 最终循迹迁移与接口统一

## 1. 为什么“从 Git 克隆”不等于复制当前全部代码

Git 克隆只会取得已经提交的版本。若参考工程还有未提交的调参修改，新目录不会自动包含这些内容。因此迁移硬件实验代码时，必须同时检查参考仓库的 `git status` 和工作区差异，不能只比较最近一次提交。

本次漏掉的工作区修改包括微分低通滤波。原工程最终使用：

$$
D_f[k]=\frac{D_f[k-1]+e[k]-e[k-1]}{2}.
$$

它保留持续的误差变化趋势，同时减弱 ADC 小幅跳动进入微分通道后的放大。

## 2. 数字传感器必须先确认有效电平

外侧 PA6 和 PB1 的 DO 在本车上是高电平表示检测到黑线。若软件按低电平有效解释，程序看到的黑白区域会完全相反，PID 参数调得再好也无法弥补这个错误。

因此硬件读取层先把原始引脚电平转换成统一语义：

```text
0：没有检测到黑线
1：检测到黑线
```

上层循迹控制器只处理这个语义，不再关心 GPIO 枚举值。

## 3. 为什么救线时内轮不能直接沿用旧值

当前实车调参使用外轮 `4500`、内轮 `1400`。内轮继续低速前进，可减轻从 PID 双轮行驶切换到急弯救线时的停车顿挫。内轮过快会增大转弯半径，内轮为零又会产生明显急停，因此该数值仍属于需要结合地图验证的实车参数。

## 4. 从救线返回 PID 为什么要同步历史

救线期间电机由固定差速控制，PID 没有连续更新。如果退出救线后仍使用救线前的旧误差，第一次微分会把整段变化当成一个瞬时变化，产生突然纠偏。

恢复时应执行：

1. 以当前 ADC 误差覆盖上一误差。
2. 清空积分和滤波微分状态。
3. 保留已经爬升的基础速度。
4. 再执行本周期 PID。

## 5. 为什么只能保留一套 PID 实现

新框架曾同时存在 `line_follow_control.c` 和旧 `car_control.c` 两套 PID。即使主流程只调用其中一套，另一套仍对外暴露接口并参与编译，后续代码一旦误调用，就会得到不同的参数和行为。

当前做法是让旧接口只承担兼容职责：它把输入交给 `LineFollowControl_Update()`，再经过安全服务和统一电机输出层执行。PID 状态、滤波和救线参数只保留一份，测试也能阻止两套接口再次分叉。

## 6. 验证边界

主机测试可以验证数值和状态切换，Keil Rebuild 可以验证 STM32 工程能够编译和链接；只有下载到开发板并跑真实赛道，才能确认传感器安装方向、电机方向、摩擦、电池和地图弯道共同作用下的实际效果。
