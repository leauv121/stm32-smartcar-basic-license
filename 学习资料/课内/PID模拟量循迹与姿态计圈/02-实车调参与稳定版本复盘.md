# 实车调参与稳定版本复盘

## 1. 复盘范围

本笔记记录实验 11.4 从传感器调节、PID 循迹、MPU6050 姿态计圈到实车调参的完整经验。最终选择的稳定基线为 Git 提交 `be2c668`，标签为 `experiment-11.4-pass-baseline`。

相关源码：

- [`Core/Src/car_control.c`](../../../Core/Src/car_control.c)：电机动作、PID 与四传感器混合循迹。
- [`Core/Src/main.c`](../../../Core/Src/main.c)：ADC、MPU6050、任务状态机、OLED 和串口调度。
- [`Core/Src/stm32f1xx_it.c`](../../../Core/Src/stm32f1xx_it.c)：SysTick 控制节拍。

## 2. 传感器调节比软件调参更靠前

四个循迹模块从左到右为 PB1、PB0、PA7、PA6，其中 PB0 和 PA7 的 AO 用于 PID，PB1 和 PA6 的 DO 用于外侧急弯判断。

每个模块有两个指示灯：一个通常表示电源，另一个随比较器输出变化。调节蓝色电位器时，应让开关灯在白色区域和黑线之间稳定翻转，而不是追求旋到某个固定角度。

实车中最左侧模块曾因碰撞或环境变化失去合适阈值，重新调节电位器后恢复。这说明识别异常不一定是代码故障，还应依次检查：

1. 模块高度和朝向是否变化。
2. 环境光是否明显变化。
3. 电池电压是否下降。
4. 插线是否松动。
5. 电位器阈值是否仍能区分黑白。

本次日志中，内侧 ADC 在不同表面约为 `150` 和 `3800`，黑白区分度足够明显，因此后期抖动主要来自控制策略，而不是 ADC 无法识别颜色。

## 3. 两个内侧 AO 与两个外侧 DO 各司其职

两个内侧 AO 产生连续误差：

$$
e[k]=ADC_{right}[k]-ADC_{left}[k].
$$

PID 根据误差调整两轮速度：

$$
\begin{aligned}
PWM_{left} &= PWM_{base}+u[k], \\
PWM_{right} &= PWM_{base}-u[k].
\end{aligned}
$$

内侧 AO 适合处理直道和普通弯道，但当黑线已经跑到最外侧时，中间两路可能无法及时给出正确方向。因此加入 PB1、PA6 的 DO 作为急弯救援：外右检测到黑线时强制向右，外左检测到黑线时强制向左。

重要经验是：只依靠中间两个模拟量可以做到平滑控制，但无法可靠覆盖所有急弯；只依靠四路数字量又容易产生开关式顿挫。两者组合比单独使用任意一种更可靠。

## 4. 稳定基线的 PID 参数

稳定版本采用：

```c
Kp = 1.0f;
Ki = 0.0f;
Kd = 0.5f;
Base_Speed = 3700;
Max_Speed = 6500;
Error_Deadband = 60;
```

启动速度从 `1800` 逐步增加，每个控制周期增加 `60`，避免电机从静止瞬间跳到正常速度。进入急弯救援后再回到 PID 时，要同步当前误差并清空积分和输出，防止微分项因模式切换突然跳变。

正确的调参顺序是：

1. 先确认左右传感器、左右电机和转向方向没有接反。
2. 用保守速度跑通完整路线。
3. 单独调 `Kp`，让车能回到黑线附近。
4. 再调 `Kd`，抑制过冲和快速摆动。
5. 只有存在长期固定偏差时，才少量增加 `Ki`。
6. 一次只改变一个变量，并记录实车结果。

## 5. 为什么提速实验反而更不稳定

后续实验曾将基础速度从 `3700` 提高到 `4600`，控制周期从 `20 ms` 缩短到 `10 ms`，同时加入动态降速、误差滤波和新的急弯救援策略。

实车出现了三个问题：

- 直道抖动加重。
- 弯道识别后仍可能冲出赛道。
- 串口中的 `MISS` 持续增加，说明主循环不断错过 `10 ms` 控制请求。

日志中 MPU 单次读取最大约为 `2–5 ms`，因此 MPU 本身不是唯一瓶颈。但 OLED、串口、软件 I2C 和其他主循环任务叠加后，`100 Hz` 控制节拍的余量明显不足。PID 输出还多次跳到约正负 `3000`，并伴随 `EDGE:N/R/L` 频繁切换，对应实车上的反复纠偏和顿挫。

这次失败说明，提高控制频率不等于提高控制质量。如果任务无法稳定在一个周期内完成，更高频率只会制造更多过期请求。最终恢复 `20 ms` 控制周期和中等速度，实车表现反而更稳定。

## 6. MPU6050 的核心问题是及时消费 FIFO

DMP 持续产生姿态数据。如果生产速度高于主循环消费速度，FIFO 中会积累旧数据，车已经转弯但程序仍在处理较早的 Yaw，最终导致计圈和掉头判断滞后。

稳定方案遵循以下原则：

1. MPU 数据读取放在主循环高优先级位置。
2. 外部中断只置标志，不在中断中执行 OLED、串口或电机控制。
3. 主循环每 `10 ms` 主动补读，避免只依赖可能被合并的单比特中断标志。
4. OLED 和串口限频，不能跟随每帧姿态刷新。
5. 读取到跨越 $-180^\circ$ 与 $+180^\circ$ 的 Yaw 时，先展开相邻增量再累计。

## 7. 单轮停止转向与差速转向

稳定版本的外侧急弯救援采用：外轮 PWM 为 `4500`，内轮 PWM 为 `0`。这种动作转弯半径小，适合把已经偏离的车快速拉回，但从 PID 双轮行驶突然切到内轮停止时会产生明显顿挫。

源码中已经存在弱转函数，采用外轮 `4500`、内轮 `2800` 的双轮差速。差速转向更连续，但转弯半径也更大；如果内轮速度过高，急弯仍可能冲出。因此下一轮应把它作为独立变量验证，而不是同时提速或修改 PID。

推荐验证顺序：

1. 保留稳定基线的 PID、`20 ms` 周期和基础速度。
2. 只把外侧急弯动作从单轮停止改为差速。
3. 从较低的内轮速度开始，例如 `1200`，外轮仍保持 `4500`。
4. 若仍顿挫，可逐步提高内轮速度；若转弯半径过大，则降低内轮速度。
5. 每次实车同时观察是否出线和是否顿挫，不能只追求视觉上的平滑。

上述差速方案目前仅为待验证决策，尚未写入稳定基线。

## 8. Git 在硬件实验中的作用

硬件调参具有较强的不确定性。一个版本编译成功，并不代表它在真实赛道上更好。因此每获得一个实车通过的版本，都应立即保存提交并添加容易识别的标签。

本实验保留 `be2c668` 作为稳定基线，之后的提速与平滑实验保持未提交。当实验表现变差时，可以精确恢复源码，而不需要凭记忆反向修改参数。

建议以后继续遵守：

- 代码能编译只是第一层验证。
- 外设数据正确是第二层验证。
- 实车完整跑通才是最终验证。
- 新实验建立在稳定提交之上，一次只改一个变量。
- Keil 自动改写的本机工程配置不要与功能源码混在同一次提交中。

## 9. 串口日志应该怎样读

启动阶段 `BOOT UART OK` 之前出现的乱码，多数来自复位瞬间、串口缓存或设备尚未稳定时的无效字节。若 `BOOT UART OK` 之后的波特率和文本持续正常，就不应把开头乱码误判为主程序持续输出错误。

运行日志应重点观察：

- `L/R`：左右内侧 ADC 是否能稳定区分黑白。
- `PID`：直道附近是否接近零，还是频繁大幅正负跳变。
- `EDGE`：外侧救援是否只在急弯触发，还是在直道频繁切换。
- `YAW/DYAW/DEG`：姿态增量方向和阶段累计值是否连续。
- `MISS`：控制节拍是否因主循环阻塞而丢失。
- `MPU_MAX`：单次 MPU 读取时间是否异常增长。

## 10. 本阶段最重要的结论

最好的版本不是参数最大、功能最多的版本，而是在当前传感器、车体、电池和赛道条件下能够重复完成任务的版本。先保证稳定、保存基线，再围绕一个明确问题做单变量实验，比同时追求速度、平滑和复杂调度更容易得到可靠结果。
